# CQA — Conversation Quality Analytics

Прототип оценки работы оператора контакт-центра в чатах и звонках по настраиваемому чек-листу:
баллы, обоснования, реплики-доказательства, апелляции, пакетная оценка набора. Хакатон Freedom Broker.

- Задание — `docs/SPEC.md`; трактовки критериев — `docs/rules.md` (входят в промпт модели).
- Контракт REST API — `docs/api_contract.md`; состояние проекта и метрики — `docs/STATUS.md`.
- Репозиторий сдачи — github.com/ynsvrs/cqa-hackathon, ветка `main`. Каталог `cqa-hackathon/` — исходный фронтенд
  второго участника как он был внесён в репозиторий (история сохранена); рабочий интерфейс — `frontend/`.
- Сдача контрольного набора — `CONTROL_RUNBOOK.md`; формат организаторов — `results/dev/results.json`,
  `scripts/export_results.py`, `scripts/validate_results.py`; сценарий защиты — `DEMO.md`.

## Запуск

```
python -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env            # LLM_API_KEY=… (Anthropic) или LLM_PROVIDER=openai + LLM_BASE_URL (Ollama/vLLM)
.venv/bin/python -m pytest -q   # 232 passed
.venv/bin/uvicorn backend.main:app --reload     # http://localhost:8000 — фронтенд; /docs — OpenAPI; /api/meta — конфигурация
```

Фронтенд (`frontend/`, чистый HTML/CSS/JS, без сборки и CDN) раздаётся тем же сервером на корне. Экраны: диалоги
(загрузка набора по `group_id`, пакетная оценка с прогрессом), карточка диалога (транскрипт с флагами реплик, для
звонков — очищенный текст и перемотка плеера; по каждому критерию ответ, баллы, вес, обоснование, цитата или
проверенный участок, причина N/A, сработавшие правила; итог и секции; подача апелляции), чек-лист (версии,
редактирование, справочник `reference`, проверка на сервере, сохранение новой версии, переоценка набора ею),
апелляции (очередь, «в работу», решение с причиной, исходный и финальный итог), аналитика (по критериям, каналам,
языкам, сверка с эталоном из файла). Все данные — из API; заготовленных результатов во фронтенде нет.
Встраивание (Dynamics 365): `/?view=dialog&conversation=<id>&n=<реплика>`; с другого источника — `CORS_ORIGINS` в `.env`.

Сквозная проверка фронтенда на живом сервере (Playwright, без вызовов модели):
```
pip install -r requirements-dev.txt && python -m playwright install chromium
cp data/cqa.db data/cqa_e2e.db && DB_PATH=data/cqa_e2e.db .venv/bin/uvicorn backend.main:app --port 8010 &
.venv/bin/python scripts/e2e_smoke.py --base http://localhost:8010      # 39 проверок, консоль браузера без ошибок
```

Загрузка набора организаторов по `group_id` (при недоступности API — `data/{group_id}.json`):

```
curl -X POST localhost:8000/api/datasets/import -H 'content-type: application/json' -d '{"group_id":"DEV"}'
curl -X POST localhost:8000/api/batches -H 'content-type: application/json' -d '{"group_id":"DEV","checklist_id":"chat-quality"}'
curl 'localhost:8000/api/results?group_id=DEV&format=csv'
```

## Как устроено

| Слой | Файлы | Что делает |
|---|---|---|
| Данные | `backend/data_source.py`, `backend/db.py` | API организаторов → SQLite; транскрипты хранятся как получены; оценки, версии чек-листов, логи, апелляции неизменяемы (триггеры) |
| Предобработка | `backend/preprocess.py` | нумерация реплик, время (MM:SS / ISO), флаги (IVR, удержание, после завершения, дубли, DTMF), факты: первая реакция, паузы с предупреждением, удержание, идентификация, завершение, позиция в аудио |
| Нормализация звонков | `backend/normalize.py` | модель-корректор ASR: `text_clean` и `asr_uncertain` на реплику, кэш; оригинал не меняется; в оценке — по `NORMALIZE_CALLS` |
| Оценка | `backend/prompt.py`, `backend/evaluator.py`, `backend/validator.py`, `backend/guards.py`, `backend/hints.py` | промпт из конфига критерия + `docs/rules.md`; один вызов на критерий, параллельно; валидация ответа (N/A, ступени, цитата — дословная подстрока оригинала) с повтором; жёсткие правила по фактам (guards); голосование `VOTES`; каждый вызов в логе со стоимостью |
| Баллы | `backend/scoring.py` | единственное место расчёта: N/A с перераспределением, шкалы, секции, флаги, Decimal ROUND_HALF_UP |
| Апелляции | `backend/appeals.py` | open → in_review → confirmed \| changed, журнал; `final` пересчитывается по решениям, исходная оценка неизменна |
| API | `backend/main.py`, `backend/batches.py` | REST по контракту, пакеты с прогрессом и отменой, статика `frontend/` |
| Проверка качества | `eval/run.py`, `eval/compare.py` | сравнение с эталоном `eval/gold_tune.json`, `eval/edge_cases.json`; отчёты в `eval/reports/` |

Чек-лист — данные (`backend/checklists/default_v1.json`, версии в БД). Новый критерий любого типа
(да/нет, шкала, флаг) с N/A, guards и подсказками работает без правки кода.

## Модели: облачная, бесплатная, локальная — точность и стоимость

Провайдер переключается одной строкой `.env` — `LLM_PROVIDER=anthropic | gemini | ollama | groq | openrouter | openai`
(профили с моделью, адресом, переменной ключа и лимитами — `backend/llm/__init__.py`; любое значение переопределяется
обычной переменной, см. `.env.example`). Код оценки один и тот же. `EVAL_MODE=per_dialog` (один вызов на весь диалог)
экономит запросы на бесплатных тарифах; `RATE_LIMIT_RPM` ограничивает частоту; ошибки ключа/биллинга останавливают
пакет с понятным сообщением, 429 и 503 — ожидание и повтор.

| Роль | Модель и режим | Настройка | Точность (эталон) | Время на диалог | Стоимость одной оценки диалога |
|---|---|---|---|---|---|
| **Калибровка** промпта и правил | Anthropic `claude-opus-5-5`, per_criterion, VOTES=3 | `LLM_PROVIDER=anthropic`, `EVAL_MODE=per_criterion`, `VOTES=3` | tune 425/440 = 96.6 %, edge 87/88 | ≈ 12 с при 4 параллельных (≈ 35 с чистого времени) | ≈ $0.30 (8 вызовов × 3 голоса, ≈ $0.10 за голос) |
| **Контроль** (prod, freeze-2) | Gemini `gemini-3.8-flash` (или `gemini-3.6-flash`), per_dialog, VOTES=1 | `LLM_PROVIDER=gemini`, ключ `GEMINI_API_KEY` | **40/40** по критериям на 5 edge-чатах RU/KZ/EN (звонки и tune не измерены — квота) | 53–239 с, ≈ 150 с | $0 на бесплатном тарифе (20 запросов/сутки на модель); на платном ≈ $0.008 ($0.75 / $3.75 за 1M токенов) |
| **Запасной** и оценка DEV для сдачи | Ollama `qwen2.5:14b` (сборка `cqa-qwen14b`, контекст 16k), per_dialog, VOTES=1, M1 Pro 32 ГБ | `LLM_PROVIDER=ollama` (`ollama/README.md`) | tune (15 диал.) 77/120 = 64.2 %, edge 63/88 = 71.6 % (Opus на тех же: 93.3 % и 98.9 %) | ≈ 181 с, последовательно | $0 |

Локальная модель слабее на ≈ 25 п.п.: систематически теряет N/A по c02 и занижает c04/c06; при пустом `na_reason`
причина N/A берётся из `reasoning` (флаг `na_reason_derived`). Таблица выбора модели по времени выдачи prod и квоты —
`CONTROL_RUNBOOK.md`, подробности замеров — `docs/STATUS.md` §4а.

## Точность на эталоне

Модель claude-opus-5-5 (effort high). Эталон размечен командой (статус черновика), holdout
не использовался при настройке.

| Набор | Чек-лист v1, `--votes 3` | v1 + справочник c04 (кандидат v2), `--votes 3` |
|---|---|---|
| tune (55 диалогов, 440 критериев) | **425/440 = 96.6 %**, MAE итога 2.17, точных итогов 43/55, единогласно 433/440 | 413/424 = 97.4 % на 53 оценённых диалогах (2 не оценены — закончился баланс API), MAE 1.60 |
| edge (12 случаев, 88 критериев) | **87/88**, пройдено 11/12 | **88/88**, пройдено 12/12 |

По критериям на tune (v1): c01 55/55, c02 52/55, c03 54/55, c04 49/55, c05 55/55, c06 50/55, c07 55/55, c08 55/55.
Нормализация звонков моделью-корректором на результат не влияет (звонки 22/24 с ней и без) и в оценке выключена.

Как читать: 1 голос даёт разброс до ±6 совпадений из 440 между прогонами на одинаковом промпте;
итоговые цифры сняты с `--votes 3` (ответ по критерию — голосование трёх вызовов).
Детали, история прогонов и открытые вопросы к разметке — `docs/STATUS.md`.
